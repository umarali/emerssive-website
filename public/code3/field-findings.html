Backend · C3suite_serverRails API and admin

A push to production-build is the deploy, untested, and migrations run at boot

The GitHub workflow replaces the running containers on push; the web container runs rake db:migrate && rails s, so any pending migration executes on the production database before the app answers, and a failing one is a full outage. CI skips that branch. Work merges into release; only /promote moves release to production-build.

Why it matters Nothing on release is live until someone promotes it, and everything on it goes live together, including two pending data migrations today (Bundle 6 fire IAPs from PR #950; the family theme colours once merged).

Where to look C3suite_server/AGENTS.md deploy section; .github/workflows/deploy.staging.yml; docker-compose.staging.yml; HANDOFF.md pending migrations.

The Gemfile says Rails 7.1, the lockfile says 6.1, and every Bundler run rewrites the lock

The upgrade is deliberately in progress: CI runs bundle update rails … at build time. Locally, bundle install and even bundle exec rails … re-resolve Gemfile.lock to 7.1.6, and db:migrate re-dumps db/schema.rb from whatever local server it touched.

Why it matters Committing either file by accident ships an untested framework upgrade or a wrong schema. Never git add -A in this repo; git checkout -- Gemfile.lock db/schema.rb before committing.

Where to look docs/learnings.md 2026-08-18; AGENTS.md hazard list.

Two theme stores colour the products: the bundle record for the apps, the product record for the website

bundles.configurations[:colors] is what each shipped app paints itself from at runtime (and what the Rails brand pages read); products.configurations[:colors] is read only by the website's product pages, and only its primary. Both are edited in /manage with no deploy. The apps never read accent or button; they render primary, text, headings, sub_headings, text_links and force background. Navy and gold are the website's colours only; they appear nowhere in the apps.

Why it matters A brand or theme change is a data change first and a code change second. The two stores had drifted (blue-primary Fire products, cerulean defaults, a pink background); the family theme fix on fix/family-theme-colors-2026-08 aligns them without moving any app's primary.

Where to look docs/brand/README.md and tokens.json (register); docs/brand/theme-fix-2026-08.md; app/controllers/manage/{bundles,products}_controller.rb#get_configurations.

The Manage colour form replaces the whole colour record every time someone saves it

Blank colour fields save as cerulean/black defaults, and the client-side Reset All Colors button uses a different default palette (#085ABA/#C7D0FB/#8E9CB8) from the server-side blanks (#33c3ff). Colour fields bypass strong params entirely.

Why it matters Two different default palettes already exist in the code base, which is how the stray values got into the data. Any admin save must be made from a fully filled Colors panel.

Where to look app/assets/javascripts/custom.js lines 13-21; manage/bundles_controller.rb lines 71-93.

The three worst findings from the website audit are still unfixed

Paid quiz content is not paywalled at the API (contents_controller and products#questions only check that a user is signed in); in-app purchases are recorded from any non-empty transaction_id with no receipt validation; quiz scores are wrong because answers are dropped on submit (viewed_content attempt sequence).

Why it matters Revenue and correctness. Planned as PRs into release; nothing started.

Where to look docs/web-redesign-audit/security-and-correctness.html P0 section, with file and line references.

product_image_url is a 15-minute presigned S3 URL

Shrine's S3 storage is configured without public: true, so every product image URL the API returns expires in 900 seconds. The website fetches products with no-store except the homepage, which revalidates every 600 seconds, inside the window with a five-minute margin.

Why it matters Any caching longer than 15 minutes 403s the product tiles; the Stripe product-image push hands Stripe an expiring URL. The server-side fix (public object URLs) is filed as hygiene.

Where to look config/initializers/shrine.rb; both repos' docs/learnings.md 2026-08-18; c3suite-web/app/page.tsx line 108.

The Manage IAP flow no longer writes to the bundle, so the fire bundle's purchase list goes stale

The write into the bundle's app[:iaps] is commented out and the flow calls a retired Apple API, so IAPs added since only reached each product's bundled_iap. PR #950 repairs the data by migration; the cause remains.

Why it matters Every future fire IAP will drift the same way until the Manage write is repaired or the bundle endpoint derives its list from the products.

Where to look docs/learnings.md 2026-08-13; db/migrate/20260813000001_add_missing_fire_iaps_to_bundle_app.rb.

A product in no bundle breaks the Rails product page

ProductsController#show dereferences @product_bundle.configurations before its nil guard. nremt-b-simulator (product 69) is in no bundle today.

Why it matters The server-rendered /products/nremt-b-simulator page raises; the Next.js site is unaffected because it does not use that page.

Where to look app/controllers/products_controller.rb lines 32-33; the product lists in GET /api/v1/bundles/*.

A local test rig exists and works

Docker container c3suite-test-mysql (MySQL 5.6.40, root/root, port 3306) with c3suite_test migrated; the CI env block is all the configuration Rails needs; no .env file required. Data migrations can be proven end to end by seeding the live records from a captured API response and running db:migrate and db:rollback. RSpec here shows 5 environment failures (missing Webpacker packs, activerecord-import version) that are baseline, not regressions.

Why it matters Anything that touches production data can be rehearsed against the same engine first. That is how the migration helper named write was caught colliding with ActiveRecord::Migration#write.

Where to look docs/learnings.md 2026-08-18 (rig recipe); memory notes e2e-rig-2026-08, code3-project-context.

Website · c3suite-webNext.js site

A push to main publishes the site within minutes; main is frozen and PRs go to temp-main

Amplify rebuilds on push, no CI, no tests; npm run build and npm run lint are the only checks. PR #8 (restyle) is open against temp-main, not merged; main catches up only when a deploy is intended, through /prepush.

Why it matters The diff is the verification. The purchase flow (Stripe checkout session and confirm) needs an end-to-end check before main moves.

Where to look c3suite-web/AGENTS.md; .claude/skills/prepush/SKILL.md.

The site runs mostly on API v1, the same API the shipped apps use

51 v1 call sites versus 11 v2 (2026-08-11): catalogue, identity and study content are v1; only commerce and analytics are v2.

Why it matters A v1 change made for the website reaches customers' installed apps. Run /api-consumer-check before touching a v1 endpoint.

Where to look AGENTS.md coupling section; docs/learnings.md 2026-08-11.

Two pieces that look like dead weight are load-bearing

The /api/:path* rewrite in next.config.js keeps in-app purchases working on shipped Android builds that still call code3apps.com/api/v1; middleware.ts deliberately does not bounce cookie-bearing users off /login (an expired cookie plus a redirect loops and crashes iOS Safari).

Why it matters Removing either as a cleanup breaks customers. Both are escalation paths in the review skill.

Where to look next.config.js; middleware.ts; the comments in each.

Product family is inferred from the title substring, in thirteen copies of the same function

inferFamily(title) returns ems for titles containing ems/emt/paramedic/emr, interview for interview, otherwise fire; a slug-to-family table in lib/products.ts exists but is never consulted at runtime. nremt-b-simulator is EMS only because its title contains 'emt'.

Why it matters A new product with a neutral title silently becomes Fire. Worth one shared helper and a real family field when families are next touched.

Where to look app/products/[slug]/page.tsx lines 65-70 and twelve siblings; lib/products.ts.

Neither phone has bundled Trade Gothic since 2023; both render the system font (corrected 20 August)

The four Trade Gothic files were carried on both platforms in the original project (9c591d4, September 2020): registered in UIAppFonts in ios/c3mobile/Info.plist, and shipped for Android in android/app/src/main/assets/fonts/. Both copies are gone by 11bc485 (31 July 2023) and stay gone through 8064802 (5 September 2023). The files still sit in assets/fonts/ and about 140 fontFamily rules still ask for them, but nothing bundles them on either platform: today's UIAppFonts lists only the fifteen icon fonts, project.pbxproj has no Trade Gothic reference, no .ttf is tracked anywhere under android/, and Android's only font step is react-native-vector-icons/fonts.gradle with that same icon set. Verified on all four product branches, 20 August. This corrects the earlier entry, which said Android still loaded them.

Why it matters The register's 'mobile font: Trade Gothic' describes the code, not the screen, on either platform. Putting the files back is a design decision, not a repair: it changes the typeface on every screen of all four apps and the layouts need a pass. Left as it is by the founder's call on 20 August.

Where to look ios/c3app/Info.plist UIAppFonts; ios/c3app.xcodeproj/project.pbxproj; android/app/build.gradle; assets/fonts/; the trees of 9c591d4, 11bc485 and 8064802; review board, section U5.

Two visual regressions the apps carry today, both from earlier work and neither fixed by the theme work

Course card titles render grey #808080: cardtitle was given Colors.darkGrey on 6 February 2024 (15897f2, EMT sibling 28ae6c1). It is a constant in the app, not a bundle colour, so no admin change and no part of the family theme fix reaches it. Separately, the header title view is width - 140 and paints itself in the product's primary colour (original 2020 code, eleven containers); its second line is taller than the navigation bar, so the part that hangs below shows as a short coloured ledge with a step at each side. Measured in the simulator on 20 August: screen 402 points, ledge 262 points, the difference exactly the 140. It does not depend on the typeface, which is what the earlier entry got wrong.

Why it matters The header is fixed on fix/quiz-header-band-fire and seen working in the simulator on 20 August: the title box no longer paints its own colour, the title is centred on the screen rather than in the space beside the back arrow, every header title uses one size, and the bar height is unchanged. Fire app only, local, not pushed. The grey title is still one line per branch. Both need a store release.

Where to look src/containers/bundle/style.js cardtitle; src/containers/quiz/style.js header; review board, section U5.

Why it matters Logged-in testing needs a seeded local server with a subscribed user (no production login exists), pointed at from src/utils/config.js; that pass ran the same afternoon, 17:24 to 17:49, and produced the six re-shot Fire and EMS screens now in PR #8.

A hard-coded JWT is embedded in the API client of every branch, expired since January 2021

src/services/api.js sends a literal token for user_id 158 as the bearer whenever no user token exists. It is long expired, so it grants nothing today, but it is a real token literal in shipped binaries. Separately, the app calls contents/<bundle slug>/get_chapters, which 404s (a bundle slug is not a content id) and shows up as a repeating getchapterRequest error in the Metro log.

Why it matters Remove the literal (send no header when logged out) and fix or drop the chapters call; both are small, both on all four branches.

Where to look src/services/api.js lines 8-15; Metro log of a logged-out session; curl of the endpoint returns 404 with or without the token.

Why it matters Expect it during any manual test run; 'Not Really' snoozes, 'Yes!' opens the store review.
